# Isolated BGE retriever experiment

This folder is separate from the working Streamlit app, `src/config.py`, and the original `data/chroma_db/policies` collection. Run all commands from the repository root with `.venv` active. The [workflow notebook](finetuning_workflow.ipynb) guides the same steps; executable logic lives in these modules so runs can be repeated.

For the full project history, explanations of every module/artifact, encountered issues, metrics, and current next steps, see the [detailed fine-tuning guide](../../docs/finetuning_detailed_guide.md).

## Baseline and corpus record

- The app configuration names `BAAI/bge-base-en-v1.5`. The index-building notebook invokes that checkpoint for its executed build. The existing Chroma `policies` collection has 1,887 vectors of dimension 768. A stored passage vector and a fresh local embedding from that checkpoint have cosine similarity `0.9999999767` and maximum absolute difference `1.55e-7`. The cached checkpoint revision is `a5beb1e3e68b9ab74eb54cfd186867f64f240e1a`. The collection itself stores no model identity or revision, so the numerical match is the strongest available provenance evidence.
- Existing index SQLite SHA-256: `32b4762d116ba43180b8963995efc437dc02d0f9b63ee4414424ec79cbaec72a`. Existing workbook SHA-256: `40614a91618009f24b8cb29b1c17a1f4194b05324a2de62fae6613f207bbed6c`.
- The collection workflow uses `RecursiveCharacterTextSplitter` with 1,000 character chunks and 100 character overlap. The workbook has 1,887 nonempty chunks from 192 distinct official URLs. Its 189 distinct titles are not reliable policy identifiers, so the manifest identifies policies by normalized URL.
- Existing result workbooks contain answer text-overlap scores, not retrieval Recall/MRR/nDCG. The golden answer workbook has 51 rows and 49 unique questions and has already been used in development. Those questions are excluded from synthetic generation and are **not** an independent test set. No baseline retrieval score is claimed until a fresh human test is locked.

## Workflow

1. `python -m src.finetuning.manifest` writes a versioned manifest, split map, and hashes under `src/finetuning/artifacts/`. The manifest keeps each real passage, original URL, normalized official URL, title, category, and stable IDs. Invalid or duplicate chunks are rejected and counted. The fixed seed gives 134 train, 29 development, and 29 test policies. All chunks of a URL share one split.
2. Put `OPENAI_API_KEY=...` in the project-root `.env` file; both the app and QA-generation command load it automatically. Then run `python -m src.finetuning.qa --count 250 --workers 2`. Requests are issued concurrently (two at a time by default) to the configured UF AI gateway; this workload is network-bound, so threads avoid the process startup and memory costs of multiprocessing. The worker count is configurable from 1 to 8; increase cautiously if the gateway allows it, because rate limits can cause failures. Requests ask for JSON mode and allow up to 1,200 tokens, retrying empty or malformed output once with a 2,000-token cap. If the returned supporting quote is not verbatim, the workflow retries that chunk once with a stricter exact-copy instruction. Successful rows are appended immediately and generation resumes after interruption. The count is the total selected target, so rerunning the same command skips already-saved chunks. Failures are printed with their reason and written to `artifacts/qa_failures.v1.jsonl`; a later run retries those chunks. `UF_AI_BASE_URL` can override the endpoint. Every record contains a question, draft answer, exact supporting quote, positive chunk ID, policy ID, title, URL, and original passage. Draft answers are synthetic and are **not** indexed or official policy statements. Exact quote membership, metadata, URL provenance, IDs, structure, and duplicate questions are checked automatically. Semantic support and ambiguity require a human review of every pilot example against the official page. Set `review_status` to `approved` or `rejected` only after adding non-empty `reviewed_by` and `review_note` fields. Expand to 500–1,500 only after the pilot is sound.
3. Run a small pilot: `python -m src.finetuning.train --max-steps 10`. The command requires reviewed train examples, excludes approved development examples, and saves a new checkpoint plus metadata in `artifacts/checkpoints/pilot_v1`. Review examples before training so the recorded QA-data hash stays valid. Use `--device cpu`, `--device mps`, or `--device cuda` as needed. Use a **new** checkpoint path for subsequent runs; existing checkpoints are never overwritten. The default contrastive loss is `MultipleNegativesRankingLoss`, with distinct positive passages per training example. A larger run uses `--max-steps 0` and an appropriately new checkpoint path.
4. For model selection, compare approved development examples with `python -m src.finetuning.evaluate --development --checkpoint src/finetuning/artifacts/checkpoints/pilot_v1`. This writes a separate `development_evaluation.v1.json` and does not alter the locked-test report. Use these synthetic, human-reviewed questions for development decisions only; do not report them as final test results.
5. An assistant-reviewed generated question set can be run as a **synthetic diagnostic only** with `python -m src.finetuning.evaluate --synthetic-test --test src/finetuning/artifacts/assistant_reviewed_synthetic_test.v1.jsonl --checkpoint src/finetuning/artifacts/checkpoints/pilot_v1`. This writes `assistant_reviewed_synthetic_evaluation.v1.json`, labels the report as non-independent, and verifies that quotes and labels match held-out source passages. For the ongoing trial only, `python -m src.finetuning.index --checkpoint src/finetuning/artifacts/checkpoints/pilot_v1 --allow-synthetic-evaluation` builds the separately labeled `chroma_finetuned_synthetic_v1/policies_finetuned_synthetic` collection. Never mark generated questions as non-synthetic or present this report/index as human-tested production results.
6. Independently write `artifacts/human_test.v1.jsonl`. Each JSON line needs non-empty `question`, `positive_chunk_id`, `policy_id`, `question_type`, and `reviewed_by` fields. Use only held-out test-policy chunks; check the relevant official policy page. Do not use generated drafts or the old exposed questions. Run `python -m src.finetuning.evaluate --lock-test` once, then `python -m src.finetuning.evaluate --checkpoint src/finetuning/artifacts/checkpoints/pilot_v1`. The lock records hashes for the test questions, manifest, and policy splits, so edits to any of them invalidate it. Evaluation also verifies the checkpoint's training-data and split hashes. It ranks the **same** questions against **all** real manifest passages for both models and reports Recall@1/3/5, MRR@10, nDCG@10, per-query ranks, and category/type groups. Never tune on this locked test.
7. Only after a passing independent-human-test comparison, run `python -m src.finetuning.index --checkpoint src/finetuning/artifacts/checkpoints/pilot_v1`. This writes a distinct `artifacts/chroma_finetuned_v1/policies_finetuned` collection using real chunks only. It refuses baseline paths and existing target directories, and builds in a temporary sibling directory before publishing the finished index. Its metadata binds checkpoint weight fingerprint, vector dimension, and corpus/split hashes. For repeated experiment queries, initialize `FineTunedRetriever` once with the collection, checkpoint, and manifest hash; it validates compatibility once and reuses the loaded model. `guarded_query()` is a convenience for one-off queries. The Streamlit app now offers the separate synthetic-trial collection through its retrieval-model selector, with the original baseline as the default. The trial option is not independent-human-test evidence; compare answer quality and citations separately before considering promotion.

23-question assistant-reviewed synthetic diagnostic. The diagnostic favors
the pilot on Recall@1, Recall@3, MRR@10, and nDCG@10, but it is not an
